## 2. S-01 일반 사용자 — 문서 검색·열람

### 2.1 전제 조건 (Given)

- 테스트 계정: `user@example.com` / 비밀번호 `Test1234!`
- 색인 완료(`ready`) 문서가 1건 이상 존재 (예: `demo.md` 내용과 유사한 “RAG 청킹” 키워드 포함)
- 브라우저: Chrome 최신, 시크릿 모드 권장(캐시 영향 최소화)

### 2.2 시나리오 단계

| Step | 액터 | 화면 | 행동 | 기대 결과 (Then) | SCR |
|------|------|------|------|------------------|-----|
| 1 | 사용자 | — | `/` 접속 (미로그인) | 로그인 화면으로 리다이렉트 | 001 |
| 2 | 사용자 | 001 | 이메일·비밀번호 입력 후 [로그인] | 홈(검색) 화면 표시, GNB에 사용자 메뉴 | 002 |
| 3 | 사용자 | 002 | 검색창에 `RAG 청킹` 입력 후 [검색] | 검색 결과 화면, 건수 ≥ 1, 스니펫에 키워드 하이라이트 | 003 |
| 4 | 사용자 | 003 | 첫 번째 결과 카드 클릭 | 문서 상세, 제목·본문 렌더, URL에 `docId` | 004 |
| 5 | 사용자 | 004 | 목차 H2 항목 클릭 | 해당 앵커로 스크롤 | 004 |
| 6 | 사용자 | 004 | GNB 로고 클릭 | 홈으로 이동, 최근 검색에 `RAG 청킹` 태그 표시(선택) | 002 |

### 2.3 성공 기준 (Acceptance)

- [ ] Step 2~4를 **연속 1회 시도**로 완료 가능
- [ ] 검색 응답부터 결과 목록 표시까지 **체감 2초 이내** (PoC 환경 기준)
- [ ] 상세 화면에서 코드 블록·표가 깨지지 않음

### 2.4 시연 스크립트 (1분 버전)

1. “로그인하지 않으면 검색 화면에 들어갈 수 없습니다.” → 로그인  
2. “업로드된 내부 MD를 자연어로 찾습니다.” → `RAG 청킹` 검색  
3. “결과는 문서 단위가 아니라 **관련 구간(청크)** 단위로 보여 줍니다.” → 카드 클릭  
4. “원문은 Markdown 그대로 읽기 좋게 보여 줍니다.” → 목차 스크롤

## 3. S-02 운영자 — 문서 업로드·색인

### 3.1 전제 조건

- 테스트 계정: `admin@example.com` (Role `admin`)
- 샘플 파일: `sample-upload.md` (로컬, 10KB 이하)

### 3.2 시나리오 단계

| Step | 액터 | 화면 | 행동 | 기대 결과 | SCR |
|------|------|------|------|-----------|-----|
| 1 | 운영자 | 001 | admin 계정 로그인 | 홈 진입 | 002 |
| 2 | 운영자 | GNB | [문서관리] 선택 | 문서 목록 테이블 | 005 |
| 3 | 운영자 | 005 | [+ 업로드] | 업로드 화면 | 006 |
| 4 | 운영자 | 006 | `sample-upload.md` D&D | 진행률 100%, 성공 토스트 | 006 |
| 5 | 시스템 | 005 | 목록 자동 갱신 또는 새로고침 | 신규 행: 상태 `indexing` → 30초 내 `ready` (PoC) | 005 |
| 6 | 운영자 | 005 | 해당 행 파일명 클릭 | 상세 화면, 본문 일치 | 004 |
| 7 | 운영자 | — | 일반 사용자 계정으로 S-01 Step 3 재실행 | 업로드 문서 제목/키워드로 검색 hit | 003 |

### 3.3 성공 기준

- [ ] 업로드 후 **색인 완료까지 PoC SLA: 60초 이내** (단일 MD, 50KB 미만)
- [ ] `ready` 이전에는 SCR-003 검색 결과에 **노출되지 않음**
- [ ] S-01과 연계 시 Step 7에서 hit 확인

### 3.4 시연 스크립트 (1분 버전)

1. “운영자는 GNB에서 문서 관리로 들어갑니다.”  
2. “Markdown을 올리면 자동으로 청킹·색인됩니다.” → 업로드  
3. “상태가 ready가 되면 검색에 반영됩니다.” → 목록·상세  
4. “이제 일반 사용자 화면에서 같은 키워드로 찾을 수 있습니다.” → S-01로 전환

## 8. 설계서 프로그램 실행 결과 리뷰 (MDKeyChunker)

화면설계서 MD를 **색인·검색 파이프라인과 동일한 방식**으로 잘라, 청크 단위로 설계 내용이 유지되는지 검수한다.

```bash
# 구조 청킹만 (API 키 불필요) + 리뷰 리포트 생성
python3 scripts/review_screen_spec_output.py

# 산출물
#   docs/output/sample-screen-spec.jsonl      ← 검색/RAG용 청크 (기계 검증)
#   docs/output/sample-screen-spec-REVIEW.md  ← 사람이 P/F 체크하는 리포트
```

| 리뷰 관점 | 확인 내용 |
|-----------|-----------|
| §1.4 화면 커버리지 | 각 SCR이 최소 1개 청크에 들어갔는지 (리포트 §1 표) |
| SCR-003 가정 | 청크 미리보기가 “검색 결과 카드”로 읽히는지 (리포트 §2) |
| 경계 | mermaid·와이어 ASCII·표가 청크 중간에서 잘리지 않았는지 |
| LLM enrich (선택) | `python3 scripts/review_screen_spec_output.py --full` + `.env` API 키 |

시나리오 S-01/S-02의 “검색 hit”는 웹 UI 대신, **고유 키워드가 포함된 청크가 jsonl에 존재하는지**로 대체 검증할 수 있다.
